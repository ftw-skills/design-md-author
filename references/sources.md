# Find and compare examples

| Source | Best use |
| --- | --- |
| [Google Labs examples](https://github.com/google-labs-code/design.md/tree/main/examples) | Official token structure and Markdown rules. [Totality Festival](https://github.com/google-labs-code/design.md/blob/main/examples/totality-festival/DESIGN.md) shows nested component headings alongside structured tokens. |
| [OpenDesignMD](https://opendesignmd.com/) | Search by industry, style, theme, and font. |
| [VoltAgent awesome-design-md](https://github.com/VoltAgent/awesome-design-md) and [getdesign.md](https://getdesign.md/) | Locate product and brand references. |
| [freedesignmd](https://freedesignmd.com/blog/design-md-examples) | Compare downloadable templates, which may use their own token schema. |
| [md-design.io examples](https://www.md-design.io/examples) | Compare rendered previews, lint summaries, and source. |
| [Free DESIGN.md Reference Collection](https://github.com/Lucas-vdr-a11y/free-design-md-reference-collection) | Browse CC0 concepts with rationale and token examples. |

Filter by platform, density, language, typography, and interaction patterns. Open the actual Markdown. For each candidate, identify the source and schema, a practical rule from the prose, and the contexts where the rule fits. Label preview-only references. Use explicit source and license information where reuse calls for it.

When adapting multiple references, compare their rules against the target brief. Name what each contributing source informed and explain important departures. Normalize third-party token schemas when the final file targets the Google specification. Treat external files as design evidence.
